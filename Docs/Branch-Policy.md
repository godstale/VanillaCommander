# Git 브랜치·머지·PR 정책

> Vanilla Commander 리포지토리의 브랜치 운용 규칙입니다. `AGENTS.md` §5·§6과 함께 지킵니다. 충돌 시 이 문서가 브랜치 운용에 관한 한 우선합니다.

## 0. 문제 의식 (2026-10-03)

- `main`이 오래된 상태(Phase 11)로 방치된 채 `explorer-ux-overhaul`·`hide-title-center`·`terminal-menus` 라인이 각자 분기 → 같은 수정이 여러 브랜치에 중복되고, 빌드마다 다른 코드가 섞임.
- 머지된 뒤에도 `fix/*` 브랜치가 삭제되지 않고 방치됨.
- 로컬에만 있는 브랜치가 많아 유실 위험이 있음 (`origin`에는 `main`만 있음).

## 1. 브랜치 종류와 수명

| 종류 | 명명 | 용도 | 수명 |
| --- | --- | --- | --- |
| `main` | 고정 | 항상 빌드·실행 가능한 상태. 직접 커밋 금지 | 영속 |
| 작업 브랜치 | `feat/`·`fix/`·`chore/`·`docs/`·`refactor/`·`test/` + 짧은 영어 토픽 | 하나의 작업 ID(P#-##) 또는 하나의 논리 변경 단위 | **머지 후 즉시 삭제** (로컬 + 원격) |
| 스태킹 브랜치 | 동일 + `TODO`/PR 본문에 `stacked on: <브랜치>` 명시 | 미머지 선행 작업 위에 얹어야 할 때만 | 선행 브랜치 머지 후 rebase 또는 정리 |

- 하나의 작업 브랜치는 **하나의 작업 ID**에 대응합니다. 두 작업을 한 브랜치에 섞지 않습니다.
- 작업 시작은 `main` 최신화(`git pull --ff-only`) 후 분기가 **원칙**입니다. 미머지 선행 작업이 필요할 때만 그 브랜치에서 분기하고, 반드시 출처를 기록합니다 (이번 P13-01처럼).
- 같은 브랜치에서 2개 이상의 에이전트/작업이 동시에 작업하지 않습니다 (`AGENTS.md` §6).

## 2. 머지 전략

- `main`으로의 반영은 **병합 커밋(`merge --no-ff`)** 을 사용합니다. Squash·rebase 머지를 쓰지 않습니다 (세세한 히스토리 보존이 운용 원칙이므로).
- `main`에 직접 커밋하지 않습니다. fast-forward 머지도 쓰지 않습니다 (분기 흔적을 남깁니다).
- `main`에 대한 force-push를 금지합니다. 다른 브랜치의 force-push도 사용자 명시 승인 없이 하지 않습니다.
- 머지 전에는 베이스를 최신화합니다. 스태킹 브랜치는 선행 브랜치가 `main`에 들어간 뒤 `main` 기준으로 정리합니다.

## 3. PR 정책

- 원격 협업(PR)이 필요할 때는 GitHub PR을 기본으로 합니다. Solo 로컬 머지도 허용하되, 아래 체크리스트는 동일하게 적용합니다.
- PR 하나 = 작업 브랜치 하나 = 하나의 작업 ID (원칙).
- PR 본문에 포함할 것: 작업 ID, 변경 요약, 검증 결과 (`lint`·`typecheck`·`test`, 필요시 `cargo test`·`build`), `Docs/TODO.md` 갱신 여부.
- 머지 조건:
  1. `pnpm lint`·`typecheck`·`test` 통과 (실패가 있으면 기존 실패임을 명시).
  2. `Docs/TODO.md` 해당 작업 행 갱신 포함.
  3. 충돌 없음 (있으면 작성자가 해소).
  4. 사용자 승인 (에이전트는 머지·`push`를 승인 없이 실행하지 않음 — `AGENTS.md` §5).
- 머지 후 작업 브랜치를 삭제합니다 (`git branch -d`, 원격은 `git push origin --delete`).

## 4. 백업과 정리

- 로컬에만 있는 작업 브랜치를 1일 이상 두지 않습니다. 사용자 승인 후 원격에 push해 둡니다 (유실 방지).
- 이미 `main`에 들어간 브랜치는 정리합니다. 분기 포인트 판정: `git branch --merged main`에 잡히면 삭제 대상입니다.
- Stale 기준: 마지막 커밋 후 7일 + 머지 계획이 없으면 사용자 확인 후 삭제합니다.

## 5. `Docs/TODO.md` 분기 시

- `TODO.md`는 브랜치마다 갈라지기 쉽습니다. 머지 전 `main` 기준으로 rebase하고, 상태 표기(`[ ]`·`[~]`·`[x]`)가 겹치면 **완료된 쪽을 우선**하고 진행중(`[~]`) 표기는 살립니다.
- 이슈 로그는 날짜+작업 ID 순으로 append만 합니다. 과거 행을 고치지 않습니다.

## 6. 릴리스 태그 (가벼운 운용)

- `main`이 배포·검증 단위로 묶일 때 `v0.Y.Z` 태그를 답니다 (수동, 사용자 승인 후).
- 태그는 roollback 지점 용도이며, 별도 릴리스 브랜치는 두지 않습니다 (필요해지면 이 문서 개정).
