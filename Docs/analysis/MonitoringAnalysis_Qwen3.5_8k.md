## 3. 핵심 발생 문제 분석 (왜 3번째 질문에서 8,192에 부딪혔는가?)

### ① 시스템 프롬프트(베이스라인)의 과도한 점유 (약 4,000 토큰)
- 활성화된 **도구 8개(read, write, edit, ls, grep, find, web_search, web_fetch)** 의 JSON Schema 명세와 **`llm-wiki` 스킬 메타데이터**가 결합되면서, **아무 대화를 하지 않은 상태의 빈 프롬프트가 이미 4,007 토큰**을 차지합니다.
- 전체 윈도우가 8,192 토큰이므로, 모델이 실제로 대화나 도구 결과, 답변을 쓸 수 있는 **가용 공간은 불과 약 4,185 토큰(51%)** 밖에 남지 않는 구조적 취약점이 발생합니다.

### ② 도구 결과(대용량 마크다운 파일)의 여과 없는 인젝션
- 질문 2에서 `ontology-commands.md` (**17.7 KB**), 질문 3에서 `wiki/index.md` (**20.6 KB**)를 읽었습니다.
- 약 20KB의 마크다운 텍스트는 토큰으로 환산 시 **약 4,500 ~ 5,500 토큰**에 해당합니다.
- 단 한 번의 파일 읽기만으로도 남은 가용 컨텍스트(4k)를 즉시 초과하거나 턱밑까지 채워버립니다.

### ③ Qwen3.5의 제어되지 않은 장문 사고 과정(Thinking) 폭주
- 질문 3의 Turn 2에서 `index.md`의 거대한 목록(90여 개 강의 및 비디오 요약)을 받은 Qwen3.5 모델이 지나치게 장황한 추론에 돌입했습니다:
  - **사고 과정(Thinking) 길이**: 무려 **12,984자 (약 3,000 토큰 분량)**
  - **추론 생성 시간**: 무려 **59,479ms (약 1분)**
- Ollama에서는 모델의 사고 과정(Thinking) 토큰 또한 `eval_count`(출력 토큰)로 카운트됩니다.
- 모델이 생각하는 데만 3,000 토큰을 쓰고 실제 본문 답변을 작성하기 시작하자마자, `입력(4,098) + 출력(4,094) = 8,192 토큰`에 도달하여 생성이 강제 종료되었습니다.

### ④ 컨텍스트 압축 시 SQLite `(session_id, seq)` UNIQUE 충돌 버그 잔존
- 질문 3 시작 시점에는 압축이 성공했으나, 질문 2의 내부 턴(Turn 2, Turn 4)에서는 여전히 `UNIQUE constraint failed: entries.session_id, entries.seq` 에러가 발생하여 중간 압축이 실패하는 현상이 확인되었습니다.

## 4. 전반적 보완 대책 및 개선 권고사항 (Action Items)

이 문제를 근본적으로 해결하기 위해 다음 5가지 영역의 보완이 반드시 필요합니다:

### 1) 도구 스키마 및 시스템 프롬프트 경량화 (High Priority)
- **현상**: 8개 도구 명세만으로 4k 토큰이 소모됨.
- **개선**:
  - 도구의 `description` 및 파라미터 설명을 군더더기 없이 간결하게 축약 (도구당 설명 길이를 30~50% 압축).
  - 당장 사용하지 않는 도구(예: 웹 도구가 필요 없는 로컬 위키 작업 시 `web_search`, `web_fetch`)는 에이전트 설정에서 선택적으로 비활성화하도록 UX 가이드 제공.

### 2) 도구 출력 결과 트렁케이션(Truncation) 및 보호 메커니즘 (Critical)
- **현상**: `read` 도구로 20KB(`index.md`)를 읽자마자 턴 전체가 포화됨.
- **개선**:
  - [read.ts](file:///C:/Workspace/Projects/Fortress/src/lib/tools/read.ts) 도구에 기본 라인 수 제한(`maxLines`, 예: 기본 150줄) 또는 최대 바이트 제한(예: 8KB)을 기본 적용.
  - 대용량 파일은 모델이 `offset`/`limit` 파라미터로 나누어 읽도록 유도하여 단일 턴에서 수천 토큰이 급증하는 현상을 원천 차단.

### 3) Qwen3.5 Thinking(사고 과정) 과열 방지 시스템 프롬프트 가이드 (High Priority)
- **현상**: 목록성 문서를 볼 때 모델이 13,000자에 달하는 과도한 CoT(사고 과정)를 전개하여 출력 한도를 소진.
- **개선**:
  - 시스템 프롬프트에 사고 과정 지침 추가:
    > *"Think concisely. Avoid repeating whole file contents in the thinking process. Keep thinking under 500 words and focus directly on fulfilling the user request."*
  - Ollama 호출 파라미터에서 출력 토큰 예약량 분배를 고려하도록 유도.

### 4) 자동 압축(Compaction) 엔트리 시퀀스(`seq`) 완벽 보장 (Medium Priority)
- **현상**: 다중 도구 실행 턴 직후 압축 시 `UNIQUE constraint failed` 발생.
- **개선**:
  - 압축 엔트리를 생성할 때 `SELECT COALESCE(MAX(seq), 0) + 1 FROM entries WHERE session_id = ?` 트랜잭션을 통해 원자적으로 최신 seq 번호를 획득하도록 보완.

### 5) 12GB GPU 하드웨어에 걸맞은 컨텍스트 크기 상향 (가장 즉각적이고 강력한 해결책)
- **현상**: 사용자의 GPU는 **RTX 4070 SUPER(12GB VRAM)** 로, 현재 Qwen3.5 9B를 100% GPU에 올리고도 **3.5GB 이상의 여유 VRAM**이 남아 낭비되고 있습니다.
- **개선**:
  - 컨텍스트 크기를 **8k (8,192)** 에서 **16k (16,384)** 또는 **32k (32,768)** 로 상향 조정.
  - 16k 컨텍스트 설정 시:
    - 기본 프롬프트 4k를 제하고도 **12k(약 12,000 토큰)의 거대한 대화/도구 버퍼** 확보.
    - KV 캐시 크기는 268MB에서 약 536MB로 단 268MB 증가할 뿐이며, 3.5GB 여유 VRAM 안에 손쉽게 수용됩니다.
    - 20KB짜리 위키 문서를 읽고 1분 동안 답변을 생성해도 컨텍스트 한계에 부딪히지 않고 여유롭게 완료됩니다.

## 5. RTX 4070 SUPER (12GB) + Qwen 3.5 컨텍스트 최적 설정 가이드

현재 기본으로 설정된 **8k (8,192 토큰)** 는 12GB 외장 그래픽카드의 잠재력과 Qwen3.5 아키텍처 특성에 비해 **상당히 보수적인(작은) 크기**입니다.

### 💡 Qwen 3.5의 KV 캐시 크기 공식 & VRAM 여유 분석
Qwen 3.5 (9B) 모델은 **GQA (Grouped-Query Attention, Key-Value Heads = 8개)** 구조가 적용되어 있어, 이전 세대 모델들에 비해 **컨텍스트가 커져도 KV 캐시가 VRAM을 매우 적게 소모**합니다.

$$\text{KV Cache Bytes (FP16)} = 2 \times 32\text{ Layers} \times 8\text{ KV Heads} \times 128\text{ Dim} \times \text{Tokens} \times 2\text{ Bytes} \approx \mathbf{131\text{ KB / 1 token}}$$

- **8k (8,192 tokens)**: KV 캐시 약 **268 MB** (기본 설정)
- **16k (16,384 tokens)**: KV 캐시 약 **536 MB**
- **32k (32,768 tokens)**: KV 캐시 약 **1.05 GB (1,073 MB)**
- **64k (65,536 tokens)**: KV 캐시 약 **2.10 GB (2,147 MB)**
- **128k (131,072 tokens)**: KV 캐시 약 **4.20 GB (4,294 MB)**

### 🎯 권장 설정 조합

#### 1) 🌟 추천 1: **32k 설정 (안정성과 속도의 최적 황금비)**
대부분의 에이전트 작업(긴 문서 읽기, 다중 도구 호출, 위키 온톨로지 탐색)에서 부족함이 없으며, OOM(Out of Memory) 걱정 없이 **50~60 tokens/sec의 Full GPU 최고 속도**를 누릴 수 있습니다.

- **컨텍스트 크기 (`contextSize`)**: **`32768` (32k)**
- **압축 여유분 (`reserveTokens`)**: **`4096` (4k)** 또는 `6144` (6k)
  - *이유*: 긴 도구 출력물(grep, read)이 한 번에 2~3k 토큰 들어와도 여유롭게 받아내기 위함
- **최근 보존량 (`keepRecentTokens`)**: **`4096` (4k)**
  - *이유*: 압축(요약)이 발생해도 직전 4~6턴의 상세한 대화 맥락과 코드 스니펫이 온전히 유지됨

#### 2) 🚀 추천 2: **64k 설정 (장문 분석/초대형 코드베이스용 최대치)**
수십 개의 소스 코드나 챕터 전체를 통째로 읽혀야 하는 경우 선택할 수 있는 12GB VRAM 기준 안전 마진 한계치입니다.

- **컨텍스트 크기 (`contextSize`)**: **`65536` (64k)**
- **압축 여유분 (`reserveTokens`)**: **`8192` (8k)**
- **최근 보존량 (`keepRecentTokens`)**: **`8192` (8k)**

> **Tip**: 에이전트 편집 화면(Agent Settings)에서 컨텍스트 크기를 `32768`로 변경하신 후 실시간 모니터링 탭을 열어두시면, VRAM이 약 9.6GB 수준에서 안정적으로 유지되며 100% GPU 가속 상태로 신속하게 추론이 동작하는 것을 직접 모니터링하실 수 있습니다.
